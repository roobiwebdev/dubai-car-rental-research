01

The five laws

Nothing else in this document matters if these break. Each one is enforced in code, not in the prompt — a prompt is a request, a constraint is a guarantee.

Law 1
The AI never asserts availability

It may only repeat what check_availability() returned in the same turn. Not from memory, not from earlier in the conversation, not from the catalogue.

Enforce: the model cannot emit an availability statement without a tool result in that turn's context. Booking re-validates atomically and fails closed.
Law 2
The AI never produces a number about money

No totals, no VAT, no per-day maths, no "roughly around". Every figure is a field on the quote object returned by get_quote(). The model formats; it does not calculate.

Enforce: output filter rejects currency figures not present in the active quote payload.
Law 3
"Confirmed" is a database state, not a sentence

The word only appears after create_booking() returns a booking ID. Before that: "let me lock that in".

Enforce: the confirmation message is a template rendered from the booking record, not free text.
Law 4
Payment is confirmed by the provider, never by the customer

"I paid" / "sent it" / a screenshot of a transfer are not evidence. Only a payment-provider webhook moves the booking forward.

Enforce: booking state machine has no transition from awaiting_payment triggered by a message.
Law 5
Policy comes from the knowledge base, in approved translations

The model never composes or translates insurance, liability, deposit or fine wording. It selects an approved chunk. If there is no chunk, it says it will get a definitive answer and escalates.

Enforce: policy answers are retrieved by ID from a versioned KB, per language, human-approved.
Why these five and not "be helpful and accurate"

Every one of them maps to a way this business actually loses money: a double-booked car, an invoice that doesn't match the quote, a car dispatched against an unpaid booking, and a promise about insurance the company then has to honour. Politeness is a preference. These are the product.

The four features customers will actually notice

1. An answer in seconds at any hour. 2. A price that doesn't change later. 3. Never being told "sorry, that's booked" without an alternative in the same breath. 4. Being told about their deposit before they have to ask. Everything else is hygiene.

03

The conversation engine

Not a chatbot script. A state machine with a language model attached to the front.

Conversation state — persisted per phone number, forever

{
  customer_id, phone, language,          // detected once, switchable, never re-asked
  slots: {
    category | vehicle_id,                 // "an SUV" or a specific unit
    start_at, end_at,                      // ISO, with time — buffers depend on it
    delivery_location { pin | zone_id },
    residency: resident | tourist | gcc,
    driver_age, licence_country,
    extras[], additional_drivers[]
  },
  active_quote: { id, expires_at, total },
  active_hold:  { id, vehicle_id, expires_at },
  active_booking_id,
  documents: [{ type, status }],
  escalation: { state, ticket_id, human_id },
  last_intent, unanswered_questions[],     // multi-part messages: nothing gets dropped
  consent: { given_at, purposes[] }
}
Why state is per-customer, not per-chat

A tourist rents in March and returns in November. Their name, licence country, language and usual delivery area are already known. Never ask a returning customer anything they have already told you — that alone reads as a better company than the competition.

Router — one primary intent, secondary intents preserved

NEW_RENTAL · EXISTING_BOOKING · EXTENSION · MODIFICATION · UPGRADE · CANCELLATION
DOCUMENTS · PAYMENT · DELIVERY_STATUS · RETURN · FAQ · DEPOSIT_STATUS
ACCIDENT · BREAKDOWN · FINE_OR_SALIK · COMPLAINT · HUMAN_REQUEST · OTHER
RuleBehaviour
Accident short-circuitAny injury/collision signal, in any language, at any point in any flow, jumps straight to the accident protocol. Nothing else is processed first.
Active booking biasIf the number has a live booking, ambiguous messages resolve to EXISTING_BOOKING. "How much for 3 more days?" is an extension, not a new rental.
Multi-intentSplit, queue, answer in order. Unanswered parts stay in unanswered_questions[] until addressed.
Language switchSwitch rendering, keep every slot. Confirm the switch in one line.
Silence+2h in-window nudge → +24h utility template → release the hold and tell them.

Input handling

InputHandling
Voice noteTranscribe → confirm understanding in one line → proceed. Common in Arabic, Hindi, Urdu.
ImageClassify: identity document / damage photo / a car they want (often an Instagram screenshot) / irrelevant. Route accordingly.
Location pinReverse-geocode → confirm area name → price the delivery zone.
PDFUsually a licence or visa. Same pipeline as images.
Anything elseAsk once, plainly, what they'd like to do.

Output rules

2–5 lines. One question at a time. Reply buttons for binary choices (max 3), list messages for shortlists (max 10). Money always AED, dates DD MMM YYYY, times 24h Gulf Standard Time — identical in every language. Every message ends with a clear next step.

04

The tools

The complete surface the model is allowed to touch. It has no database access. Every write is idempotent and fails closed.

check_availability({ category?, vehicle_id?, start, end, area? })
  → { units:[{ vehicle_id, make, model, year, class, plate? }],
      alternatives:[…], checked_at }
  Failure: returns [] + alternatives. Never throws to the model as "unknown".

get_quote({ vehicle_id|category, start, end, delivery_location, extras[], promo? })
  → { quote_id, line_items[], subtotal, vat, total,
      deposit:{ type:'pre_auth'|'cash'|'none', amount },
      mileage:{ cap_per_day, overage_rate },
      not_included[], exclusions[], expires_at }
  The only source of money in the entire system.

create_hold({ quote_id })            → { hold_id, expires_at }
create_booking({ quote_id, customer_id, hold_id, payment_ref, idempotency_key })
  → { booking_id } | { error:'CONFLICT', alternatives[] } | { error:'QUOTE_EXPIRED' }
lookup_bookings({ phone })           → [ booking summaries ]
modify_booking({ booking_id, changes }) → quote | { requires_approval }
extend_booking({ booking_id, new_end }) → quote | { error:'CONFLICT', substitutes[] }
store_documents({ booking_id, media_ids[], type }) → { status:'pending_review', issues[] }
create_payment_link({ quote_id, purpose:'rental'|'deposit'|'extension' })
  → { url, expires_at }
get_charges({ booking_id })
  → { salik[], fines[], mileage_overage, fuel, deposit:{ status, release_due_at } }
schedule_delivery({ booking_id, location, window }) → { driver, eta }
dispatch_roadside({ booking_id, location, symptom }) → { ticket_id, eta }
escalate({ reason, priority, payload }) → { ticket_id }

Failure behaviour — specified, not improvised

FailureWhat the customer sees
CONFLICT on bookingHonest apology + 2–3 alternatives with prices in the same message. Never "please try again".
QUOTE_EXPIRED"That price expired — here's the current one" with a fresh quote, not silence.
Tool timeoutOne "checking that now" message, then retry. Two failures → escalate. Never invent an answer while waiting.
Payment link fails twiceOffer an alternative method, then escalate to a human.
Any unhandled errorEscalate. The model never sees or repeats a stack trace, tool name or error code.
05

Availability & money

The two things that must be impossible to get wrong.

Availability: make double-booking structurally impossible

Not a check in application code — a constraint the database will not let you violate, including the buffers on both ends.

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    vehicle_id WITH =,
    tstzrange(start_at - prep_buffer, end_at + turnaround_buffer, '[)') WITH &&
  ) WHERE (status IN ('held','confirmed','active'));

Availability is derived, never stored. A unit is free for a window only if there is no overlapping row in bookings, maintenance or damage_blocks. Blockers to model:

BlockerTypical size
Turnaround (clean, inspect, refuel)1–3 hours, per class
Delivery / collection travel30 min – 3 hours, per zone
Scheduled serviceFleet calendar
Mulkiya (registration) renewalUAE-specific, annual, blocks the unit
Damage / accident repairOpen-ended until closed
Current renter running lateThe most common real-world cause of a broken promise — never assume an on-time return for a same-day handover
Hold lifecycle

Quote issued → 30-minute hold (longer for rare/exotic units) → expiry stated in the message → auto-release → customer told it was released. A hold that expires silently is worse than no hold.

Money: one object, start to finish

quote  →  booking  →  final statement
  same line-item schema throughout — the invoice is the quote plus actuals

line_items: [
  { code:'RENTAL_DAILY',  qty:4, unit:99.00, amount:396.00 },
  { code:'DELIVERY',      zone:'marina', amount:0.00 },
  { code:'VAT',           rate:0.05, amount:19.80 }
]
deposit: { type:'pre_auth', amount:1000, release_due_at:'2026-10-02' }
mileage: { cap_per_day:250, overage_rate:1.50 }
not_included: ['SALIK','TRAFFIC_FINES','FUEL']
exclusions:   ['TYRE_RIM_DAMAGE']            // stated up front, not after the damage
expires_at:   '2026-09-01T18:40:00+04:00'
The acceptance test that matters most

Quoted total must equal invoiced total, minus only actual usage (Salik, fines, mileage overage, fuel), every single time. Any deviation is a P1 bug, not a rounding discussion. This is the one thing that makes customers trust the whole system.

Payment & deposit — who is allowed to do what

ActionOwner
Explain deposit type and amountA AI, from the quote
Generate and send a payment linkB Backend → provider. Never a fabricated URL
Create the pre-authorisation holdB Backend → provider
Confirm payment receivedB Provider webhook only
Record cash on deliveryDriver, in the dashboard
Release the hold / refund a depositD Finance, named approver. AI reports status only
Any refund or goodwill waiverD Human, always

Support three payment shapes from day one, because all three exist in this market: full prepay, deposit pre-auth + pay on delivery, and pay entirely on delivery. Pay-on-delivery raises no-show risk — mitigate with a confirmation reply required 2 hours before dispatch.

Replies inside the customer-initiated 24-hour window are free (plus 1,000 free service conversations/month). Utility templates are cheap. Marketing templates are not — keep them rare and deliberate. Budget for Meta charging in-window service and utility messages from 1 Oct 2026.

  escalation : { reason, priority, triggered_at, agent_summary },   // one plain sentence
  customer   : { name, phone, language, type, nationality, vip, previous_rentals },
  booking    : { id, vehicle, plate, start, end, delivery_location,
                 payment_status, deposit_status, documents_status },
  financial  : { total_paid, outstanding, salik_accrued, fines[] },
  conversation:{ transcript_url, last_10_messages, intents[], sentiment },
  location   : { lat, lng, shared_at },
  attachments: [ handover_photos, police_report_pending ]
}

While a human is active the AI is silent. On release it is re-briefed with what the human did, so it never contradicts them. A human can also mark a customer permanently AI-blocked.

Accident protocol — the exact script

1. "Are you and your passengers safe?" — always first, always alone. 2. If anyone is hurt: call 999, nothing else matters. 3. Don't move the car unless police direct you, or damage is minor with no injuries and it's blocking traffic. 4. A police report is mandatory — insurance won't cover the damage without one. 5. Send your location. 6. Escalate.
Never discuss fault, excess, coverage, or who pays. Those need a human and a police report.

The one thing that can sink this project

Weeks 1–2. If availability lives in a spreadsheet or in a manager's head, the AI cannot be truthful and no amount of prompt engineering fixes it. Do not start the conversation layer until there is a queryable source of truth. If the client has no system, that is the first deliverable — and it is worth building regardless of whether the agent ever ships.
